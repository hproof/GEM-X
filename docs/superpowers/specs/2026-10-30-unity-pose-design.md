# 单图与目录姿态识别及 Unity Humanoid 接入设计

日期：2026 年 10 月 30 日。

## 一、已确认的目标

提供简单的命令行入口，输入一张图片或一个目录，生成静态人体姿态。第一版仅使用 Body 模型，其 77 个关节已包含身体、双手和手指，不调用独立 Hand 模型，不做两套预测的融合。

识别结果同时保存为项目原生 `.pt` 和自定义姿态 JSON。同一份 JSON 有两个出口：

1. Unity 编辑器读取后生成真正的 Humanoid 动画片段，再按目标平台打包为 AssetBundle。
2. 游戏运行时读取 JSON，转换并设置目标 Humanoid 角色的骨骼旋转。

第一版不需要 FastAPI、专用网页、Blender 或 FBX。图片批处理不是动作序列，不把多张独立图片自动拼成连续动画。

## 三、方案选择

选择“通用源骨架姿态 JSON，加 Unity 共用映射模块”。Python 不依赖具体 Unity 角色；目标角色的骨骼轴向和参考姿态由 Unity 侧处理。

不采用“Python 直接输出某个角色的局部旋转”作为交换协议，因为这会把 JSON 绑定到某个 Avatar。不采用 FBX 中转，因为两条已确认的使用流程均可直接从 JSON 完成。

## 四、命令行入口

新增薄封装脚本 `scripts/pose_image.py`，提供两个子命令：

```bash
# 识别一张图片。
python scripts/pose_image.py infer --input /path/person.jpg --output-dir outputs/poses

# 递归识别目录，并记录吞吐率。
python scripts/pose_image.py infer --input /path/images --recursive --output-dir outputs/poses

# 从已有 Body 预测导出 JSON，无须重新加载识别模型。
python scripts/pose_image.py export --input /path/body.pt --output-dir outputs/poses
```

`infer` 支持 `--checkpoint`、`--soma-assets`、`--body-detector`、`--device`、`--detector-device`、`--intrinsics` 和 `--overwrite`。资源默认值从仓库位置解析，不依赖调用者当前工作目录。保持自动人体检测的主人物选择规则；第一版每张图片处理一个主要人物。

目录输入默认只处理当前层，`--recursive` 才遍历子目录。支持的后缀固定为 JPG、JPEG、PNG、BMP、WEBP、TIF、TIFF，忽略后缀大小写；文件按相对路径稳定排序。

输出保留输入相对目录，并将原始扩展名包含在文件名中。例如 `a/person.jpg` 生成 `a/person.jpg.pt` 和 `a/person.jpg.pose.json`，避免与 `a/person.png` 冲突。

默认不覆盖已有完整结果；跳过项记入报告。若只有部分结果存在，视为冲突并报告，使用 `--overwrite` 明确重新生成。禁止把输出目录重新纳入输入遍历。单文件输出先写临时文件，再替换为最终文件。

第一版按图片串行推理，模型、检测器和几何运行时在进程内复用，不逐图重新加载。目录批处理与张量批量推理明确区分，不把此版本描述成多图并行推理。

`export` 接收单个 `.pt` 或目录，验证输入格式及任务，第一版仅接受 Body 的单图结果，每个结果仅包含一个人物。拒绝 Hand 结果和视频结果，并给出中文说明。

## 五、输出协议

每张成功图片输出一个原生 `.pt` 和一个 `.pose.json`，整次执行输出 `report.json`。JSON 使用 UTF-8，带独立的协议版本及源骨架版本。

姿态 JSON 至少包含以下信息：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 交换协议版本，第一版固定为 `gemx_unity_pose_v1` |
| `source` | 图片名称、尺寸、模型标识、SOMA 版本、参考姿态版本 |
| `coordinates` | 单位、坐标轴定义、旋转空间和四元数顺序 |
| `joints` | SOMA 公共骨架的 77 个关节，顺序与预测一致 |
| `name`、`parent_index` | 唯一关节名称及父节点索引，Hips 为根，父索引为 -1 |
| `reference_world_rotation` | 关节参考姿态的全局旋转 |
| `posed_world_rotation` | 关节预测姿态的全局旋转 |
| `reference_root_relative_position` | 同一身份及骨长下、相对 Hips 的参考位置 |
| `posed_root_relative_position` | 相对 Hips 的预测位置，供校验和调试 |
| `camera_translation` | 按导出坐标基转换后的相机平移，保留作调试数据，默认不应用到游戏角色 |

四元数统一使用 `[x, y, z, w]`，归一化，数值必须有限。导出后的旋转及位置统一为 Unity 轴向：X 向右、Y 向上、Z 向前，单位为米。转换从项目声明的相机轴向推导，旋转使用矩阵基变换，不能凭经验翻转若干四元数分量。

所有全局旋转处于共同的模型参考坐标空间，不是 Unity 场景世界空间。SOMA 的虚拟 Root 在推导变换时处理，最终只输出与 Body 结果一致的 77 个公共关节。

原始参数旋转不是 Unity 的最终 `localRotation`。Python 必须通过与 Body 推理一致的 SOMA 路径恢复参考和姿态变换，处理关节方向、参考姿态及中间骨骼，再导出公共关节旋转。重建的预测关节应与 `.pt` 保存的关节匹配。

## 六、Unity 运行时接入

以可复制的工具包形式提供运行时和编辑器代码，分别放在独立目录及程序集；运行时代码不得依赖 `UnityEditor`。兼容设计以 Unity 2022.3 LTS 及更新版本为基线，实际验证版本以可用的目标项目为准并记录。

运行时组件接收角色的 `Animator`，要求其 Avatar 有效且为 Humanoid。通过 `HumanBodyBones` 查找目标骨骼，通过 Avatar 的参考骨架数据建立目标参考姿态，不把当前播放动画的某一帧当成参考姿态。无法建立参考骨架时明确失败。

建立集中维护的 SOMA 到 Humanoid 映射表，覆盖躯干、头颈、肩臂、腕、腿足及两手各三段手指。左右侧使用相同规则：

| SOMA 关节 | Humanoid 骨骼 |
| --- | --- |
| `Hips` | 髋部 |
| `Spine1`、`Spine2`、`Chest` | 脊柱、胸部、上胸 |
| `Neck2`、`Head` | 颈部、头部 |
| `Shoulder`、`Arm`、`ForeArm`、`Hand` | 肩、上臂、前臂、手腕 |
| `Leg`、`Shin`、`Foot`、`ToeBase` | 大腿、小腿、足、脚趾 |
| `HandThumb1`、`HandThumb2`、`HandThumb3` | 拇指近端、中段、远端 |
| 其他手指的第 2、3、4 节 | 对应手指近端、中段、远端 |

除 Hips 和躯干之外，上表中省略的左右前缀按实际关节名称补齐。SOMA 多于 Humanoid 的颈部、掌骨、末端及其他中间关节，需要通过源全局变换正确折叠，不能简单删除后直接使用原局部旋转。手指映射以参考位置和骨段方向做额外验证，不能只以名称相似判断正确。

目标可选骨骼不存在时跳过并报告；Humanoid 必需骨骼或核心映射缺失时拒绝应用。不把脸部、眼睛和下颌表情纳入第一版姿态驱动。

映射模块结合源参考旋转、源姿态旋转和目标参考旋转求目标旋转，再按照目标真实父子关系计算局部旋转。角色保留自己的骨长、局部位置和缩放。角色 GameObject 的场景根位置和旋转保持；Hips 的朝向和倾斜仍作为模型根坐标空间中的骨骼姿态应用，不生成根运动。

提供一次性应用和持续保持两种方式。持续保持在 `LateUpdate` 应用，避免被 Animator 当帧更新覆盖；不主动关闭整个 Animator。该方式仍需与项目中其他后处理、IK 或骨骼控制脚本明确执行顺序。

JSON 不绑定某个具体角色，但姿态映射结果需要结合目标 Avatar 求解；不能承诺同一份源四元数直接赋值到所有 Humanoid 角色。

## 七、Unity 编辑器出口

提供选择姿态 JSON、目标 Humanoid 角色及输出目录的编辑器入口，复用运行时映射模块，在临时角色实例上应用静态姿态。

通过 `HumanPoseHandler` 获取目标 Avatar 的人体姿态，生成基于 Humanoid 肌肉曲线的 `.anim`，而不是仅包含某个模型骨骼路径的普通动画。静态片段长 1 秒，在首尾写入相同采样值，不生成位置移动或根运动。保存后重新读取并检查动画是否为 Humanoid 动画。

人体肌肉表示可能有约束或范围限制，因此必须将生成的片段重新采样到同一角色，与直接应用 JSON 的结果比较，报告映射骨骼的角度误差。超出默认 5 度的最大误差时报告不通过，可通过参数显式调整阈值；不静默把明显不一致的片段标为成功。

提供单独的 AssetBundle 构建入口，输入已有 `.anim` 和目标平台。目标平台必须显式选择；AssetBundle 不能视为跨平台通用文件。第一版打包生成的片段，不自动包含用户角色模型。构建使用独立构建映射，不修改用户原有资源的 Bundle 标签。

## 八、性能统计与错误处理

使用单调时钟记录资源初始化、每张图片的检测、推理、JSON 导出、保存及总耗时。GPU 计时边界显式同步，避免异步 CUDA 调用造成虚假的吞吐率。

报告分别给出总尝试数、成功数、未检测到人物数、失败数、跳过数、模型初始化耗时、首张耗时、后续成功图片的平均值及分位数、总吞吐率和持续处理吞吐率。持续处理指标排除初始化、首张及跳过项，包含后续实际尝试的失败和未检出项耗时。没有足够样本时输出空值，不输出误导性的零或无穷大。

坏图片、单图未检出人物或导出失败，不中断整个目录；报告图片路径和中文原因。空目录、模型或资产缺失、协议不兼容等全局配置错误立即失败。全部成功或仅有明确跳过时返回 0；存在图片级失败或未检出时返回 1；全局配置错误返回 2。

显存不足时停止本次批处理并保存已完成项的报告，不自动切换到 CPU 后混合计算 GPU 吞吐率。第一版不增加并发任务、自动降精度或多 GPU 调度。

## 九、代码边界与部署方式

- Python 批处理、JSON 协议和源骨架导出分别放入职责独立的模块，CLI 仅负责参数解析和调用。
- Unity 的协议结构、骨骼映射、运行时应用、动画烘焙和资源打包分别组织。
- 不改变已有 `gem-infer` 及原生 `.pt` 的格式或行为。
- 所有新增文档、注释、错误提示和日志使用简体中文。
- Windows 仓库保存开发修改；部署到 Linux 仓库前检查目标工作区，只同步本任务相关文件，不覆盖用户自己的改动。
- 推理继续使用既有 `gem-x` 环境，无须增加训练、Open3D 或 Blender 依赖。

## 十、验证与验收

1. 使用真实图片执行单图推理，验证 `.pt` 和 JSON 均包含非空人体及手指姿态。
2. 使用包含多张有效图片、坏图片、无人物图片及同名不同扩展名文件的目录验证输出、报告和退出码；验证递归和覆盖规则。
3. 验证目录处理期间模型只加载一次；在 RTX 3060 上记录实测吞吐率，注明样本数和是否含初始化。
4. 用已有 `.pt` 独立导出，确认不加载 DINOv3 或识别权重。
5. 验证父子图无环、关节顺序和名称正确、四元数归一化、左右侧及坐标基转换正确。通过 SOMA 重建的相机空间关节与保存结果的最大位置偏差不超过 0.1 毫米。
6. 在 Unity 中以两个骨长或骨骼轴向不同的有效 Humanoid 测试参考姿态、单轴旋转、身体和手指映射；检查运行时保持模式与 Animator 的执行顺序。
7. 生成 `.anim`，检查 Humanoid 类型、1 秒静态采样及直接应用与片段回放的一致性。
8. 为明确平台打包 AssetBundle，重新载入并取出动画片段，验证可播放。
9. 保存验证报告，区分 Python 已验证、Unity 已验证和仅完成代码检查的部分；未运行 Unity 时，不声称 Unity 接入及打包已通过。
