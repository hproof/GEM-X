# 单图与目录姿态识别及姿态 JSON 导出设计

日期：2026 年 10 月 30 日。

## 一、已确认的目标

提供简单的命令行入口，输入一张图片或一个目录，生成静态人体姿态。第一版仅使用 Body 模型，其 77 个关节已包含身体、双手和手指，不调用独立 Hand 模型，不做两套预测的融合。

识别结果同时保存为项目原生 `.pt` 和自定义姿态 JSON。JSON 保留将来接入 Unity Humanoid 所需的信息，后续可供两个出口使用：

1. Unity 编辑器读取后生成真正的 Humanoid 动画片段，再按目标平台打包为 AssetBundle。
2. 游戏运行时读取 JSON，转换并设置目标 Humanoid 角色的骨骼旋转。

本次仅实现 Python 命令行识别、目录处理、JSON 导出和性能报告，不实现 Unity 侧代码、动画片段生成或 AssetBundle 打包，也不需要提供 Unity 项目路径。

第一版不需要 FastAPI、专用网页、Blender 或 FBX。图片批处理不是动作序列，不把多张独立图片自动拼成连续动画。

## 三、方案选择

选择“通用源骨架姿态 JSON”。Python 不依赖具体 Unity 角色；将来接入 Unity 时，目标角色的骨骼轴向和参考姿态由 Unity 侧处理，相关实现不属于本次范围。

不采用“Python 直接输出某个角色的局部旋转”作为交换协议，因为这会把 JSON 绑定到某个 Avatar。不采用 FBX 中转，因为两条已确认的使用流程均可直接从 JSON 完成。

## 四、命令行入口

新增薄封装脚本 `scripts/pose_image.py`，提供两个子命令。`infer` 可以缩写为 `i`，`export` 可以缩写为 `e`；所有业务选项均提供明确的短选项：

```bash
# 识别一张图片。
python scripts/pose_image.py infer -i /path/person.jpg -o outputs/poses

# 递归识别目录，并记录吞吐率。
python scripts/pose_image.py i -i /path/images -r -o outputs/poses

# 从已有 Body 预测导出 JSON，无须重新加载识别模型。
python scripts/pose_image.py e -i /path/body.pt -o outputs/poses
```

| 长选项 | 短选项 | 含义与适用命令 |
| --- | --- | --- |
| `--input` | `-i` | 图片、预测文件或目录；两个子命令均支持 |
| `--output-dir` | `-o` | 输出根目录；两个子命令均支持，默认 `outputs/poses` |
| `--recursive` | `-r` | 递归处理输入目录；两个子命令均支持 |
| `--checkpoint` | `-c` | Body 权重；仅识别命令 |
| `--soma-assets` | `-s` | SOMA 资产目录；两个子命令均支持 |
| `--body-detector` | `-b` | 人体检测器；仅识别命令 |
| `--device` | `-d` | 推理或几何计算设备；两个子命令均支持，默认 CUDA |
| `--detector-device` | `-D` | 检测器设备；仅识别命令，默认 CPU |
| `--intrinsics` | `-k` | 相机内参文件；仅识别命令 |
| `--help` | `-h` | 中文帮助 |

长选项保留完整形式，不接受任意长选项前缀截断，避免新增参数后原命令含义发生变化。资源默认值从仓库位置解析，不依赖调用者当前工作目录。保持自动人体检测的主人物选择规则；第一版每张图片处理一个主要人物。

目录输入默认只处理当前层，`--recursive` 才遍历子目录。支持的后缀固定为 JPG、JPEG、PNG、BMP、WEBP、TIF、TIFF，忽略后缀大小写；文件按相对路径稳定排序。

每次实际处理都在 `-o` 指定的根目录下创建独立的执行目录，名称为“子命令加本地时间戳”，例如 `infer_20261030_153012_123`。时间戳精确到毫秒，创建目录使用原子操作；同名冲突时追加 `_001` 等递增后缀，绝不复用旧目录。报告记录带时区偏移的开始时间，程序启动和结束时打印实际输出路径。帮助和参数解析失败不创建执行目录。

本次执行生成的预测、JSON、报告及错误记录全部放入该执行目录。执行目录内部保留输入相对目录，并将原始扩展名包含在文件名中，避免同名不同扩展名冲突。例如：

```text
outputs/poses/
└── infer_20261030_153012_123/
    ├── report.md
    └── a/
        ├── person.jpg.pt
        ├── person.jpg.pose.json
        ├── person.png.pt
        └── person.png.pose.json
```

每次执行目录都是全新的，因此不提供覆盖旧执行结果或断点续跑选项。同一输入再次执行会进入新的时间戳目录。输入列表在处理前生成固定快照，输出根目录位于输入目录内部时排除该输出子目录，避免递归读入历史或本次生成的结果。单文件输出先写临时文件，再替换为最终文件。

第一版按图片串行推理，模型、检测器和几何运行时在进程内复用，不逐图重新加载。目录批处理与张量批量推理明确区分，不把此版本描述成多图并行推理。

`export` 接收单个 `.pt` 或目录，验证输入格式及任务，第一版仅接受 Body 的单图结果，每个结果仅包含一个人物。拒绝 Hand 结果和视频结果，并给出中文说明。

## 五、输出协议

识别命令中，每张成功图片输出一个原生 `.pt` 和一个 `.pose.json`；独立导出命令只写新的 `.pose.json`，不复制已有 `.pt`。两种命令均在各自的时间戳执行目录内输出 `report.md`，由脚本直接生成供人阅读的中文 Markdown。姿态 JSON 使用 UTF-8，带独立的协议版本及源骨架版本。

姿态 JSON 至少包含以下信息：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | 交换协议版本，第一版固定为 `gemx_unity_pose_v1` |
| `source` | 图片名称、尺寸、模型标识、SOMA 版本、参考姿态版本 |
| `coordinates` | 单位、坐标轴定义、旋转空间和四元数顺序 |
| `joints` | SOMA 公共骨架的 77 个关节，顺序与预测一致 |
| `name`、`parent_index` | 唯一关节名称及父节点索引，Hips 为根，父索引为 -1 |
| `reference_world_rotation` | 关节参考姿态的全局旋转 |
| `posed_world_rotation` | 关节预测姿态的全局旋转 |
| `reference_root_relative_position` | 同一身份及骨长下、相对 Hips 的参考位置 |
| `posed_root_relative_position` | 相对 Hips 的预测位置，供校验和调试 |
| `camera_translation` | 按导出坐标基转换后的相机平移，保留作调试数据，默认不应用到游戏角色 |

四元数统一使用 `[x, y, z, w]`，归一化，数值必须有限。导出后的旋转及位置统一为 Unity 轴向：X 向右、Y 向上、Z 向前，单位为米。转换从项目声明的相机轴向推导，旋转使用矩阵基变换，不能凭经验翻转若干四元数分量。

所有全局旋转处于共同的模型参考坐标空间，不是 Unity 场景世界空间。SOMA 的虚拟 Root 在推导变换时处理，最终只输出与 Body 结果一致的 77 个公共关节。

原始参数旋转不是 Unity 的最终 `localRotation`。Python 必须通过与 Body 推理一致的 SOMA 路径恢复参考和姿态变换，处理关节方向、参考姿态及中间骨骼，再导出公共关节旋转。重建的预测关节应与 `.pt` 保存的关节匹配。

## 六、为后续 Unity 接入保留的数据边界

本节只描述 JSON 的用途边界，不交付 Unity 运行时组件、编辑器工具、C# 代码或工具包。

JSON 必须保存源骨架的参考姿态、预测姿态和完整父子层次，便于未来依据目标 Avatar 计算骨骼旋转。它不是某个具体 Humanoid 角色可直接逐项赋值的局部旋转数组。

本次不折叠或删除 SOMA 中多于 Humanoid 的颈部、掌骨、末端等关节，不绑定具体 Avatar，也不生成 Humanoid 肌肉值。未来 Unity 侧可以利用完整源全局变换处理不同骨骼层次和轴向。

## 七、性能统计与错误处理

使用单调时钟记录资源初始化、每张图片的检测、推理、JSON 导出、保存及总耗时。GPU 计时边界显式同步，避免异步 CUDA 调用造成虚假的吞吐率。

报告分别给出总尝试数、成功数、未检测到人物数、失败数、模型初始化耗时、首张耗时、后续成功图片的平均值及分位数、总吞吐率和持续处理吞吐率。持续处理指标排除初始化和首张，包含后续实际尝试的失败和未检出项耗时。没有足够样本时显示 `—`，不输出误导性的零或无穷大。

按用户后续确认，报告补充每张图片的宽、高、像素数、格式后缀及精确文件字节数。未检出时保留可读尺寸，坏图尺寸未知时显示 `—`。独立导出时尺寸来自预测记录，字节数明确指输入 `.pt` 文件。吞吐率以张/秒为主，原图百万像素/秒作为辅助；后者不代表固定裁剪尺寸的网络计算能力，独立导出不提供像素吞吐率。终端同时显示排除首张后的平均耗时与持续成功吞吐率。

坏图片、单图未检出人物或导出失败，不中断整个目录；报告图片路径和中文原因。空目录、模型或资产缺失等全局配置错误立即失败；独立导出时单个输入协议不兼容属于文件级失败。全部成功时返回 0；存在文件级失败或未检出时返回 1；全局配置错误返回 2。

显存不足时停止本次批处理并保存已完成项的报告，不自动切换到 CPU 后混合计算 GPU 吞吐率。第一版不增加并发任务、自动降精度或多 GPU 调度。

## 八、代码边界与部署方式

- Python 批处理、JSON 协议和源骨架导出分别放入职责独立的模块，CLI 仅负责参数解析和调用。
- 本次不新增 Unity 工具、动画烘焙或资源打包功能。
- 不改变已有 `gem-infer` 及原生 `.pt` 的格式或行为。
- 所有新增文档、注释、错误提示和日志使用简体中文。
- Windows 仓库保存开发修改；部署到 Linux 仓库前检查目标工作区，只同步本任务相关文件，不覆盖用户自己的改动。
- 推理继续使用既有 `gem-x` 环境，无须增加训练、Open3D 或 Blender 依赖。

## 九、验证与验收

1. 使用真实图片执行单图推理，验证 `.pt` 和 JSON 均包含非空人体及手指姿态。
2. 使用包含多张有效图片、坏图片、无人物图片及同名不同扩展名文件的目录验证输出、报告和退出码；验证递归规则。
3. 验证目录处理期间模型只加载一次；在 RTX 3060 上记录实测吞吐率，注明样本数和是否含初始化。
4. 用已有 `.pt` 独立导出，确认不加载 DINOv3 或识别权重。
5. 验证父子图无环、关节顺序和名称正确、四元数归一化、左右侧及坐标基转换正确。通过 SOMA 重建的相机空间关节与保存结果的最大位置偏差不超过 0.1 毫米。
6. 验证短选项、完整长选项及子命令别名行为一致；帮助使用中文，含糊的长选项截断被拒绝。
7. 连续执行两次，验证每次生成独立时间戳目录，所有产物均在对应目录；模拟同毫秒名称冲突，验证不会覆盖旧目录。
8. 保存 Python 验证报告，不将 JSON 的坐标约定校验描述为已完成 Unity 接入验证。
